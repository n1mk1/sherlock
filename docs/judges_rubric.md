# Nebius × NVIDIA Hackathon
## Judging Rubric & Evaluation Report

**Source:** "Will It Ship" — Hackathon Judges Panel  
**Duration:** ~57 minutes  
**Purpose:** Understand how judges assess submissions and translate their feedback into an actionable evaluation rubric.

---

## 1. Executive Summary

The judges evaluate submissions across four official criteria:

1. Technological Implementation
2. Design
3. Potential Impact
4. Quality of the Idea

The strongest submissions demonstrate:

- A real problem affecting a clearly identified audience.
- A focused, functional solution with a compelling use case.
- Meaningful integration of Nebius and NVIDIA technologies.
- An intuitive, complete user experience.
- A creative approach grounded in domain knowledge.
- Evidence of testing, reliability, and measurable value.

**Core principle:**

> A simple, well-executed product solving a meaningful problem can outperform a technically complex project with unclear value.

**Important:** The panel did not specify official numeric weights, minimum technology counts, or scoring thresholds.

# 2. Official Judging Criteria

## Criterion 1: Technological Implementation

### Official Description

How well is the project built, and how effectively does it use Nebius and NVIDIA Nemotron?

### What Judges Look For

- Effective implementation of selected technologies.
- Genuine use of platform capabilities.
- Appropriate technical architecture.
- Creative applications of supported models and tools.
- Working features rather than superficial API integrations.
- Clear technical reasoning behind architectural choices.

### Strong Submission Characteristics

- Models are selected for specific purposes.
- Every integration serves a defined function.
- Core functionality works reliably.
- The implementation uses platform strengths.
- Engineering complexity is justified.
- Technical trade-offs are understood.

### Common Weaknesses

- Importing tools without using their capabilities.
- Adding unnecessary technologies.
- Building a complex system for a simple task.
- Features that appear functional but fail during execution.
- Inability to explain why particular models were chosen.

### Judge Insights

**Jackie:**
Technological implementation means actually using the features and strengths of the platform, rather than merely importing tools.

**Ricky:**
Creative and unexpected implementations are particularly compelling.

**Johnny:**
Expressed interest in agentic workflows, local models, physical AI, and robotics.

### Evaluation Questions

- Does the technology materially enable the solution?
- Is the model or service selection justified?
- Is the architecture appropriate for the problem?
- Does the core workflow function?
- Is there a technically meaningful implementation?

## Criterion 2: Design

### Official Description

Is the project a complete and coherent product experience, rather than merely a technical proof of concept?

### What Judges Look For

- Intuitive user interfaces or developer interfaces.
- Clear onboarding and instructions.
- Easy navigation and understandable workflows.
- Meaningful visual hierarchy.
- Consistent product behavior.
- Clear communication of system status and results.
- A coherent end-to-end experience.

### Strong Submission Characteristics

- Users immediately understand what the product does.
- The first meaningful action is obvious.
- Users reach the "aha moment" quickly.
- The interface exposes important results prominently.
- Loading, errors, and progress are communicated.
- Additional technical details are available without overwhelming users.
- Design decisions reflect the target audience.

### Timing Guidance

**30 seconds:**
Aim to communicate the product's compelling value or "wow" moment.

**Under 2 minutes:**
Aim for a new user to understand the product and experience its principal value.

These are recommendations expressed during the panel, not formal timing requirements.

### Common Weaknesses

- Generic AI-generated UI design.
- Complicated onboarding.
- No sample inputs or examples.
- Unclear buttons and actions.
- Missing progress indicators.
- Important actions buried beneath lengthy explanations.
- Dense reports without visual interpretation.
- Attractive interfaces with unclear utility.

### Judge Insights

**Selena:**
A strong design allows users to understand a product's impact through a simple and intentional experience.

**Sushmita:**
The design should get users to the "aha moment" in under two minutes.

**Jackie:**
If users cannot understand how or why to use the product immediately, that can reduce its evaluation.

### Evaluation Questions

- Can someone unfamiliar with the product use it?
- Is the first action obvious?
- Is the main result easy to find?
- Are the system's actions and progress visible?
- Does the experience feel complete?
- Is the interface appropriate for its intended audience?

## Criterion 3: Potential Impact

### Official Description

Does the project make a credible, specific case for solving a real problem for a real audience?

### What Judges Look For

- A clearly defined user or customer.
- A meaningful, demonstrable problem.
- An understanding of existing pain points.
- Clear user benefits.
- Practical relevance and potential adoption.
- Evidence that the solution improves an existing process.

### Strong Submission Characteristics

- Identifies a specific target audience.
- Explains the current workflow and its shortcomings.
- Demonstrates a useful improvement.
- Shows why the problem matters.
- Provides evidence supporting the value proposition.
- Connects product features to user outcomes.
- Explains how the solution could be used outside the hackathon.

### Common Weaknesses

- Building technology without a clear reason.
- Targeting an overly broad audience.
- Making unsupported impact claims.
- Adding features that do not improve the core outcome.
- Failing to differentiate from existing alternatives.
- No feedback from potential users.

### Judge Insights

**Selena:**
Potential impact was her personally preferred criterion, emphasizing empathy and real users.

**Ricky:**
The important question is not simply whether something can be built, but whether it should be built.

**Jackie:**
Builders should clearly articulate the user, the problem, and the main improvement.

### Evaluation Questions

- Who specifically benefits?
- What problem does the product solve?
- Why does that problem matter?
- How is the problem currently addressed?
- What measurable or observable benefit is created?
- Why might users choose this solution?

---

## Criterion 4: Quality of the Idea

### Official Description

Is the project a creative, nonobvious use of the platform that demonstrates real understanding of the problem?

### What Judges Look For

- Original problem-solving approaches.
- Understanding of difficult domain challenges.
- Knowledge of technology trade-offs.
- Appropriate use of platform strengths.
- Meaningful differentiation from existing products.
- Insights that go beyond generic AI application patterns.

### Strong Submission Characteristics

- Addresses a narrowly defined challenge effectively.
- Demonstrates real subject-matter understanding.
- Offers a creative technical or product approach.
- Explains the difficult parts of the problem.
- Makes thoughtful engineering trade-offs.
- Has a distinct and credible value proposition.

### Common Weaknesses

- Generic AI chatbot wrappers.
- Reproducing existing tools without improvements.
- Technology-first ideas without domain understanding.
- Unnecessary feature expansion.
- Impressive concepts without executable value.
- Originality claims unsupported by differentiation.

### Judge Insights

**Sushmita:**
A strong idea demonstrates knowledge of the hard parts of the problem, including model choices, model sizes, and cost-control trade-offs.

**Johnny:**
Solving a smaller practical problem well can be better than attempting a very large, unfocused idea.

**Ricky:**
Understanding the market and speaking with potential customers is fundamental.

### Evaluation Questions

- What makes the idea nonobvious?
- Is the problem understood deeply?
- Why is the proposed approach better suited to the problem?
- What alternatives and trade-offs were considered?
- What insight makes this solution distinct?
- Can the idea deliver meaningful real-world value?

# 4. Lessons from Reviewed Projects

## 4.1 Telltale — Scam Detection

### Strengths

- Clear problem and audience.
- Easy-to-use sample inputs.
- Evidence-backed findings.
- Intuitive visual hierarchy.
- Actionable recommendations.
- External verification of model-generated claims.

### Weaknesses and Opportunities

- Recommended actions appeared too far down the page.
- The interface was information-dense.
- Integration into communication workflows could increase usefulness.
- More explicit handling of uncertain evidence would build trust.
- A more distinctive visual identity could improve differentiation.

### Key Lesson

**Prioritize the user decision and recommended action before extensive explanations.**

---

## 4.2 Slash-agent — Cost-Aware Coding Agent

### Strengths

- Concrete optimization problem.
- Task-level model routing.
- Transparent execution receipts.
- Potential for measurable cost savings.

### Weaknesses and Opportunities

- Onboarding was unclear.
- Execution progress was difficult to follow.
- Model routing was not sufficiently visible.
- Cost savings lacked a clear comparison baseline.
- Concurrent-use limitations caused friction.

### Key Lesson

**Show the measurable benefit, explain how it was achieved, and compare it against a meaningful baseline.**

---

## 4.3 Mnemos — Auditable AI Memory

### Strengths

- Distinctive visual design.
- Transparent memory references.
- Ability to inspect and delete memories.
- Potential cross-agent memory through MCP.
- Strong technical and design concept.

### Weaknesses and Opportunities

- Main use case was initially unclear.
- Product impact required additional explanation.
- External integrations could make its value more concrete.
- User-session and memory-isolation behavior needed clarification.

### Key Lesson

**A technically interesting product needs an immediately understandable value proposition.**

---

## 4.4 Assay — Robotics Data Quality

### Strengths

- Specialized real-world problem.
- Objective data-quality checks.
- Detailed technical analysis.
- Practical relevance for robotics workflows.

### Weaknesses and Opportunities

- More guided onboarding was needed.
- Report interpretation was difficult.
- Charts and visual diagnostics could improve usability.
- Clearer corrective recommendations would increase usefulness.

### Key Lesson

**Transform complex technical outputs into understandable findings and next actions.**

# 5. Additional Evaluation Principles

## 5.1 Technology Quantity Does Not Equal Quality

Judges did not advocate a minimum number of technologies.

A smaller technical stack can be better if it solves the problem effectively.

Use additional integrations only when they contribute meaningfully to the core experience.

## 5.2 Scope Discipline Is Important

A single understandable workflow can outperform a collection of loosely related capabilities.

Every feature should support the principal value proposition.

## 5.3 Real-World Testing Matters

Ask people unfamiliar with the project to attempt its core workflow.

Observe:

- Where they hesitate.
- What they misunderstand.
- Whether they complete the main task.
- Whether the outcome is useful.
- Which explanations are missing.

## 5.4 Documenting Failure Is Positive

Judges specifically appreciated transparent discussion of:

- Failed test cases.
- Known limitations.
- Unsupported scenarios.
- Technical trade-offs.
- Future improvements.

This demonstrates engineering rigor and genuine testing.

## 5.5 Terminal Applications Can Demonstrate Strong Design

A web frontend is not required to demonstrate good UX.

For terminal-focused products, prioritize:

- Information hierarchy.
- Clear navigation.
- Readable outputs.
- Relevant model attribution.
- Performance and operational metrics.
- Minimal unnecessary clutter.

## 5.6 Accessibility Should Be Considered

Judges value accessibility, although the panel did not expect every prototype to be production-grade.

Accessibility improvements should be clearly demonstrated or documented.

## 5.7 Final Submission Quality Matters

The final project narrative should explain:

1. The problem.
2. The intended audience.
3. The solution.
4. The technical architecture.
5. The demonstrated result.
6. The product's differentiation.
7. Its limitations and future potential.

# 8. Final Submission Checklist

## Problem and Impact

- [ ] Clearly identified target audience.
- [ ] Clearly described real-world problem.
- [ ] Demonstrated meaningful user benefit.
- [ ] Explained the limitations of existing alternatives.
- [ ] Collected feedback from potential users.

## Technical Implementation

- [ ] Appropriate use of Nebius and NVIDIA technology.
- [ ] Core system is functional.
- [ ] Each integration has a defined purpose.
- [ ] Technical architecture is understandable.
- [ ] Important engineering trade-offs are documented.
- [ ] Known failures and limitations are recorded.

## Design

- [ ] Main value is apparent quickly.
- [ ] New users can begin without extensive guidance.
- [ ] Results and next steps are prominently displayed.
- [ ] Loading and execution states are visible.
- [ ] Interface matches the intended audience.
- [ ] Error and edge-case behavior has been considered.

## Quality of Idea

- [ ] Specific and focused use case.
- [ ] Meaningful differentiation.
- [ ] Strong problem understanding.
- [ ] Appropriate technical and product decisions.
- [ ] No unnecessary feature expansion.

## Final Presentation

- [ ] Clear project description.
- [ ] Functional demo.
- [ ] Concise explanation of architecture.
- [ ] Examples of realistic inputs and outputs.
- [ ] Evidence supporting product value.
- [ ] Honest description of limitations.
- [ ] Future development roadmap.
- [ ] All submission materials reviewed.

# 9. Final Recommendations

Prioritize improvements in this order when time is limited:

1. **Core functionality:** Ensure the main workflow works consistently.
2. **Clarity of value:** Make the problem and result understandable immediately.
3. **User experience:** Reduce friction and improve onboarding.
4. **Evidence:** Demonstrate measurable or observable improvements.
5. **Differentiation:** Explain the insight that makes the idea valuable.
6. **Technical explanation:** Show how and why the chosen technology is used.
7. **Submission packaging:** Deliver a compelling, accurate project narrative.

Avoid adding features unless they materially improve a judging criterion.

---

# 10. Final Takeaway

A strong Nebius × NVIDIA Hackathon submission should combine four qualities:

**Technically meaningful + Intuitively designed + Genuinely impactful + Creatively differentiated**

The project does not need to be enormous.

It needs to solve a real problem, work reliably, communicate its value clearly, and demonstrate thoughtful engineering decisions.
